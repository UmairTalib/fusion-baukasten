Was ist Fusion-Baukasten?

Fusion-Baukasten (auch: deliberAIde) ist eine KI-gestützte, browserbasierte Planungsplattform für Bürgerbeteiligungsformate — entwickelt an der Universität Siegen. Der Name bedeutet wörtlich: ein modularer Baukasten für partizipative Planungsprozesse.

Kernunterschied zu bestehenden Tools

Bestehende Plattformen (DIPAS, CitizenLab, Consul) sind Durchführungstools — sie helfen bei der Ausführung von Beteiligungsveranstaltungen. Fusion-Baukasten ist ein Planungstool: Es unterstützt bei der Konzeption, Strukturierung und Vorbereitung — bevor die Veranstaltung beginnt. Das ist die Lücke im Markt.

Kritisch: Status-Label-System im Kontext-Bereich

Jeder von der KI extrahierte Kontext-Eintrag trägt ein Status-Label. Der Planungs-Agent darf ausschließlich ÜBERNOMMENE Einträge verwenden — nie VORSCHLAG oder KONFLIKT. Dies ist das Herzstück des Human-in-the-Loop-Prinzips und muss korrekt implementiert sein, bevor die Agenten produktiv genutzt werden.

KI-Agenten-Architektur
4-Agenten-System mit LangGraph — asynchron, Human-in-the-Loop.

Das 4-Agenten-System

AgentRolleTrigger-BedingungOutput
🧠 Planungs-Agent Zentraler Orchestrator. Führt den gesamten Dialog durch alle 7 Blöcke A–G. Erstellt Block-Summaries. Koordiniert alle anderen Agenten. Immer aktiv (Hauptagent) Block-Summaries, Dialog-State, Output-Koordination
Zielgruppen-Agent Erstellt strukturierte Zielgruppenprofile mit Barrieren, Erreichbarkeit, Bedarfen. Greift auf Barrieren/Kanal-Matrix zu. Block C: Zielgruppe unklar ODER sehr breit formuliert (z.B. "alle Bürger") AudienceProfile mit Traits, Barriers, Needs
Strategie-Agent Methoden-Matching aus 113-Format-Katalog. Empfiehlt Top-3-Formate. Erstellt Kommunikationsstrategie + Risikohinweise. Block D: Zielgruppen-Profil vorhanden UND Format noch unklar StrategieEmpfehlung, KommunikationsStrategie, Risiken
Kontext-Agent Analysiert hochgeladene PDFs/DOCX. Führt Web-Recherchen durch. Setzt Status-Labels (VORSCHLAG). Erkennt Konflikte automatisch. Datei-Upload ODER "Hintergrund ergänzen" ODER erkannte inhaltliche Lücken Kontext-Einträge mit VORSCHLAG-Label

Asynchroner Workflow

Agenten-Aufrufe dauern 2–30 Sekunden. Synchrone HTTP-Requests wären für das Frontend unzumutbar. Daher: asynchrones Job-Queue-Modell via Celery.

1. Nutzer gibt Antwort │ ▼ Dialog Engine ← prüft Trigger-Bedingungen nach jedem Turn │ ├── Trigger erkannt? ──► agent_calls Tabelle: Status = pending │ │ │ ▼ │ Celery Worker ← holt Job aus Queue │ │ │ ┌──────────────┼──────────────┐ │ ▼ ▼ ▼ │ Zielgruppen-Agent Strategie-Agent Kontext-Agent │ │ │ │ │ └──────────────┴──────────────┘ │ │ LLM-Aufruf + Validierung │ ▼ │ Status → done │ Output → DB gespeichert │ └── Frontend: WebSocket-Event ─OR─ Polling /dialog/agent-status/{projekt_id} │ ▼ UI aktualisiert Agenten-Status-Panel in Echtzeit

Rückpropagierung

Wenn ein Nutzer im späteren Dialog eine frühere Antwort ändert (z.B. Zielgruppe in Block C nach Block E), muss das System automatisch betroffene Bereiche markieren:

# Abhängigkeitskette (aus Planungs-Agent Spezifikation) Zielgruppe ─► Format ─► Outreach ─► Agenda ─► Location # Bei Zielgruppen-Änderung → alle nachgelagerten agent_calls # werden als "outdated" markiert → Nutzer sieht Warnung "Dadurch ändern sich folgende Bereiche: Format, Outreach, Agenda"

Wann kommt der OpenAI API-Key?

Bis der OpenAI-Key verfügbar ist, arbeiten alle 4 Agenten mit Mock-Responses — strukturierte, statische Antworten, die die echte API-Antwort simulieren. Das ermöglicht die vollständige Entwicklung des Dialogs, der Datenbank und der UI, ohne einen Cent auszugeben.
