Project Overview and What It Does
What is Fusion-Baukasten? Analysis of all source documents. Full user journey.

What is Fusion-Baukasten?

Fusion-Baukasten (also called deliberAIde) is a German-language, AI-powered, browser-based platform for planning civic participation events. It is developed at Universitat Siegen and targets German municipalities, NGOs, civic planners, and university researchers.

The Market Gap This Fills

Tools like DIPAS, CitizenLab, and Consul help people run participation events. No tool on the market helps planners decide which format to use, how to reach their audience, and what the event should look like before it starts. Fusion-Baukasten fills that gap using AI-guided dialogue. That is the core value proposition.

What the Project Documents Got Wrong

Non-Technical Suggestions Corrected

The project documents were written by domain experts, not software engineers. The following suggestions from the docs have been overridden with better decisions:

Spark (mentioned for chat logic) — Spark is a no-code chatbot prototyping tool, not suitable for production. Replaced by LangGraph + FastAPI.

Airtable or Firebase (mentioned as database options) — Both lack the relational integrity, query power, and GDPR control needed here. PostgreSQL is the correct choice.

pip as package manager — Replaced with uv, which is 10-100x faster and has better dependency resolution for complex AI/ML stacks.

Socket.IO (from original plan) — Unnecessary abstraction. FastAPI has native WebSocket support that covers all real-time requirements here.

Critical: The 3-State Status Label System (Domain 4)

Every fact extracted by the Context Agent is tagged with a label. The Planning Agent is only permitted to read ACCEPTED entries — never SUGGESTION or CONFLICT. This is how the Human-in-the-Loop principle works in practice: the AI proposes, the human confirms, and only then does data influence recommendations. This must be implemented correctly before agents go live.

06
AI Agent Architecture
4-agent system via LangGraph. Async via Celery. Human-in-the-Loop enforced.

The 4-Agent System

AgentRoleWhen TriggeredOutput
Planning Agent Central orchestrator. Drives the entire dialogue through blocks A-G. Creates block summaries. Decides when to call specialist agents. Always active — the main agent Block summaries, dialogue state, output coordination
Audience Agent Creates structured audience profiles including barriers (mobility, language, digital access), reachability, and participation needs. Block C: target group is unclear or too broadly defined (e.g. "all citizens") AudienceProfile with traits, barriers, participation needs
Strategy Agent Matches project context to the 113-format method catalogue via pgvector semantic search. Recommends top 3 formats with justification, communication strategy, and risk notes. Block D: audience profile exists AND format is still undecided StrategyPackage: recommendations, communication plan, risks
Context Agent Parses uploaded PDFs and DOCX files. Runs optional web research. Tags each extracted fact as SUGGESTION. Auto-detects conflicts with existing ACCEPTED data. File uploaded, or user clicks "Add background", or system detects content gap after a block summary Context entries with SUGGESTION label, conflict flags

Async Agent Workflow

LLM calls take 2-30 seconds. Users cannot wait for a synchronous HTTP response. All agent work runs asynchronously via Celery:

User submits a dialogue answer | v [ Dialog Engine ] checks trigger conditions after every turn | +-- Trigger detected? | | | v | Write to agent_calls table -> status = pending | | | v | [ Celery Worker ] picks job from Redis queue | | | +----------+----------------+ | v v v | Audience Strategy Context | Agent Agent Agent | | | | | +----------+----------------+ | | LLM call + Pydantic validation | v | status -> done | output written to DB | v Frontend receives update via: WebSocket event (preferred, real-time) -- or -- Polling /api/dialog/agent-status/{project_id} every 2s

Back-Propagation (Change Cascading)

When a user changes an earlier answer after completing later blocks, the system automatically detects and flags affected downstream decisions:

# Dependency chain (from Planning Agent specification) Target Group -> Format -> Outreach -> Agenda -> Location # On target group change: all downstream agent_calls marked outdated # User sees a warning in the UI: "This change affects: Format, Outreach Strategy, Agenda. Please review."

6-Month Development Roadmap
6 phases. Week-by-week breakdown. July 2026 to January 2027.
Solo Developer Strategy

Every phase delivers a working vertical slice — not just infrastructure. The OpenAI API key is not needed until Phase 3. Until then, all agents use structured mock responses so the full dialogue flow, database, and UI can be built and tested at zero AI cost.

Foundation — Repository, Docker, Database
Weeks 1-3 · approx. 45 hours

  • docker-compose.yml: PostgreSQL 16, Redis 7, Nginx, placeholder web and api services
  • Scaffold Next.js 14 with TypeScript and Tailwind CSS in apps/web
  • Scaffold FastAPI with uv in apps/api — pyproject.toml not requirements.txt
  • Alembic setup: first migration creates all 8 database domains
  • pgvector extension enabled in PostgreSQL
  • Seed script: import 113 methods from Austauschformate-v2.xlsx into methods table with embeddings
  • JWT authentication: login endpoint, guest mode, refresh tokens
  • Login screen as first functional frontend page (matching V.05 prototype design)
  • .env.example with all required variables documented and commented
2
Core Flow — The 7-Block AI Dialogue
Weeks 4-7 · approx. 60 hours
  • Planning Agent with LangGraph — mock LLM responses, no API key needed yet
  • 7-block dialogue structure A-G with adaptive branching logic
  • Express Mode (3-5 questions) vs. Detailed Mode (all 7 blocks)
  • Block summary logic after each block: Decided / Open / Risks
  • Frontend: Core Flow view — conversational UI, chip selection, one question per screen
  • All dialogue answers saved to database with autosave snapshots
  • Progress indicator showing current block and completion percentage
  • Recap logic: every 3-5 turns, offer a summary for user confirmation
3
AI Sub-Agents — Full 4-Agent System
Weeks 8-11 · approx. 70 hours
  • Audience Agent: profile generation with barrier and channel matrix
  • Strategy Agent: semantic method matching against 113-format catalogue via pgvector
  • Context Agent: PDF and DOCX upload parsing with PyMuPDF and python-docx
  • 3-state status label system: SUGGESTION, ACCEPTED, CONFLICT enforced at DB level
  • Celery workers for all async agent calls with retry logic
  • WebSocket: real-time agent status in the Co-Pilot panel
  • Back-propagation engine: cascading change detection and user warnings
  • YAML prompt files versioned in the repository — no hardcoded prompts
  • OpenAI API key integrated — GPT-4o-mini for most tasks, GPT-4o for complex reasoning
